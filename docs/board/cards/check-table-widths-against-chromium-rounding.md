# Check the table widths against Chromium's rounding

- **Created:** 2026-11-18
- **Status:** Open

## Why

The user opened this card on 2026-11-18 and put it in Next. The point
was noticed by the agent on 2026-11-17, while measuring the code font
for the card
[hide the wrap toggle on blocks that fit](hide-the-wrap-toggle-on-blocks-that-fit.md),
and left open in that session's minute.

Chromium on Linux turned out to round each character of the code font
to whole pixels, so the page was drawn narrower or wider than the
build assumed. The build estimates the tables' widths in the same way,
from the advance of each character, to decide when a table becomes a
record viewer. If Chromium rounds the table's characters too, at some
text sizes a table could be drawn wider than the build estimates and
overflow its column, which breaks the page; at others the record
viewer would show earlier than needed, which the user accepted on
2026-11-17 as harmless (card
[measure the fonts again when they change](measure-the-fonts-again-when-they-change.md)).

## What is known

- **How the tables are estimated.** `src/table_widths.rs` adds up the
  advance of each character: Literata's, from `src/literata_widths.rs`,
  generated by `end2end/tools/measure-literata-widths.mjs`, which
  measures each character alone on a canvas at 1000 pixels in
  Chromium; and Hack's, 1233/2048 of an em at 85% of the text, for
  inline code. Kerning is ignored, so the estimate errs on the wide
  side.
- **What Chromium does with the code font.** Measured on 2026-11-17 on
  Linux, Chromium 158 of Playwright: inside the code block every
  character of Hack is drawn a whole number of pixels wide, the
  nearest to the true one, narrower at some sizes and wider at others.
  With `text-rendering: geometricPrecision` it draws the true width;
  since 2026-11-18 the rule is on the code block only
  (`style/input.css`), not on the tables nor on inline code.
- **Not checked:** whether Chromium also rounds Literata's characters,
  a proportional font, and inline code inside a table; and whether a
  measure taken on a canvas at 1000 pixels reflects what the page draws
  at the text's size.
- **What already guards the tables.** The browser tests `exactly one
  form of each table` and `the form of the simple, six-column and
  limit tables at` (`end2end/README.md`) fail when a table is wider
  than its column; the table of texts at the limit is built just under
  the column at 767 pixels, with words in italic, inline code and
  bold. They pass today, at the site's own text sizes only.

## Questions to answer

The ones known when the card was written; there may be more.

- **Whether Chromium rounds the characters of a table** to whole
  pixels, Literata's and inline code's, at the site's sizes and at
  the others a reader can reach by changing the browser's text size.
- **Whether a table can then overflow its column** without becoming a
  record viewer, at any size, and by how much.
- **What to do if it can**, for example the same rule given to the
  code block, or a margin in the estimate, without making the record
  viewer show much earlier than needed.
