# Measure the fonts again when they change

- **Created:** 2026-11-16
- **Status:** Closed
- **Closed:** 2026-11-18

## Why

The user opened this card on 2026-11-16, while cutting the card
[link the fonts to the build](../done/2026-11-16_link-the-fonts-to-the-build.md),
and put it in Next, after the fonts page. On 2026-11-17 it became the
last card on the fonts before the style guide is published.

Some values of the build are measured on a font, and would not follow
a change of font made in the configuration:

- the table widths are estimated from Literata's character widths
  (`src/literata_widths.rs`), measured in Chromium by
  `end2end/tools/measure-literata-widths.mjs`;
- the wrap toggle of the code blocks shows from a threshold computed
  with Hack's advance, 1233/2048 of an em.

Comments of the stylesheet also name the fonts where they explain a
measure.

## What is known

Checked in the code on 2026-11-17. The configuration
(`config/fonts.txt`) says `text=literata`, `code=hack`,
`logo=ibm-vga-8x16`; the description of each font
(`config/fonts/<folder>.txt`) holds no measure, and nothing ties the
measured values below to the font the configuration names.

- **The table widths.** `src/literata_widths.rs` is generated by
  `end2end/tools/measure-literata-widths.mjs` and read by
  `src/table_widths.rs`, which also holds by hand Hack's advance,
  1233/2048 of an em, for inline code in a table.
- **The wrap toggle of the code blocks.** `src/markdown.rs` holds
  Hack's advance by hand (`CODE_ADVANCE_NUMERATOR`, 1233, over 2048).
- **The stylesheet's comments.** `style/input.css` names Literata or
  Hack where it explains a measure; one comment also gives a number,
  0.602em, the width of the zero in Hack.
- **The logo font.** No width measured on it was found in the code.
- **A change of font already stops the build today, but not for the
  measures.** The author's text of the fonts page
  (`content/style-guide/fonts.md`) has one piece per font and role,
  `## <folder> | <role>`; a font in a role with no piece stops the
  build (`MissingPiece` in `src/style_guide/fonts_page.rs`). Once the
  text is written, the build passes again with the old measures.
- **The browser tests already check the outcome of the measures on the
  style guide's cases** (`end2end/README.md`): `each one scrolls or
  fits as written` fails when a block of the code page that should
  scroll does not show the wrap toggle, or a block that fits shows it;
  `exactly one form of each table` fails when a table is wider than
  its column; `the form of the simple, six-column and limit tables at`
  fails when the table of texts at the limit, built just under the
  column at 767 pixels, is wider than its column. They catch a wrong
  measure only when a case sits near the threshold it moves.

- **Chromium on this machine draws Hack narrower than the build
  assumes.** Measured on 2026-11-17 by a sub-agent, on the built code
  page, before any case was written: at 17 pixels (the code at 768
  pixels and over) each character is 10 pixels wide, against the
  10.234 pixels of 1233/2048 of an em; at 15.3 pixels it is 9 pixels.
  The likely cause, not checked: the advances are rounded to whole
  pixels, which depends on the platform. At 768 pixels and over the
  scroller is 686 pixels wide: a line of 67 characters fits with no
  toggle, one of 68 fits (680 pixels) but shows the toggle, one of 69
  overflows and shows it. The case pair agreed below (one character
  apart, the first fitting with no toggle, the second overflowing with
  it) does not exist on this machine. Measuring scripts:
  the session's scratchpad, not kept. The fault was fixed on
  2026-11-18 by the card the agent opened for it (see
  "Dependencies"), and the pair exists since.

## Questions to answer

The ones known when the card was written; there may be more.

- **Whether a change of the text font or of the code font should stop
  the build until its measures are taken again.**

  **Answered by the user on 2026-11-17.** It should break, but not
  always: whether it breaks depends on the stylesheet and on the nature
  of the font. What matters is how the page is laid out: a new font may
  cause no problem with the stylesheet as it is, while with another
  stylesheet (text inside a box of a fixed size, for example) something
  may break.

- **Whether estimates made too cautious by a narrower font count as a
  broken page.** Came up on 2026-11-17. A font wider than the one
  measured makes the estimates too low, and the page breaks: a table
  overflows its column, a block of code scrolls without the wrap
  toggle. A narrower font makes them too cautious: the page works, but
  worse than it could.

  **Answered by the user on 2026-11-17.** It depends: caution counts
  when it leads to a result that is hard to read. For the record
  viewer it does not count. The wrap toggle on a block that fits
  counts, and keeps stopping the build as it does today: it takes
  space, and what can be avoided is better avoided.

- **How the build notices that the code font's measure no longer
  fits the page.** Came up on 2026-11-17. The tables have a case at
  the limit, just under the column at 767 pixels; the code page has
  none: its cases are a line longer than the column and a block that
  always fits, both far from the threshold, so a code font somewhat
  wider or narrower than Hack would pass unnoticed.

  **Answered by the user on 2026-11-17.** By the outcome only: two
  cases at the limit on the code page, a line that fills the column
  exactly and one a character longer, and the toggle must show on the
  second only. Rejected: a tool that measures the configured font and
  stops the build when its measures differ from those in use, because
  it would stop the build also when the page is right, against the
  answer above.

- **Where the measures come from.** Came up on 2026-11-17. Today
  Hack's advance is written by hand in two files, and the generated
  widths hold for Literata only.

  **Answered by the user on 2026-11-17.** More precise measures would
  be better, taken from the font the configuration gives each role,
  whatever it is: a change of font means running the measure again,
  not writing a value by hand. The other reading of the answer,
  measures that also cover the fallback font the browser shows until
  the site's font arrives, is not what was meant. The measures are
  taken in the build, in the browser, as the script for Literata does
  today. This work left the card (see "What it leaves").

## Acceptance tests

Agreed with the user on 2026-11-17. On 2026-11-18 the user moved tests
1 to 4 and 6 to the card
[hide the wrap toggle on blocks that fit](../done/2026-11-18_hide-the-wrap-toggle-on-blocks-that-fit.md),
which writes the two cases as its regression test; they stay here as
the record of what was agreed, and are met when that card is closed.
This card keeps test 5 only.

1. **The case that fits.** The code page of the style guide has a
   block whose longest line is the longest that fits the column at the
   width chosen for the cases; at that width the block does not scroll
   and shows no wrap toggle.
2. **The case one character longer.** A second block has the same line
   with one character more; at the same width it scrolls and shows the
   wrap toggle.
3. **The width chosen.** The cases are measured at the widest column
   (768 pixels and over), where the line is longest, so one character
   is the smallest share of it and the test notices the smallest
   difference.
4. **At the other column widths** both cases do what their text says
   (at a narrower column both scroll and show the toggle), checked by
   the existing test `each one scrolls or fits as written`, extended to
   the new cases.
5. **Proof that the guard works.** With Hack's advance in the build
   changed on purpose so the threshold moves by one character, in
   either direction, the test fails; both failures are shown to the
   user, then the value is put back.
6. **The browser tests' README** (`end2end/README.md`) describes the
   new cases in the test's row, and `end2end/tests/readme.spec.ts`
   passes.

Known limit: the guard notices a difference only when it is worth at
least one character over the longest line. A code font almost as wide
as Hack passes, and the page stays right, as the rule above asks.

- **The proof that the guard works** (test 5) was run on 2026-11-18
  by a sub-agent on Haiku, on the built site, with the test `each one
  scrolls or fits as written`, and shown to the user; the value was
  then put back, and nothing of it was committed:
  - Hack's advance in the build (`CODE_ADVANCE_NUMERATOR` in
    `src/markdown.rs`) at 1234 over 2048 instead of 1233: the build
    counts the line of 67 characters as 686.3 pixels, over the 686 of
    the column, and the test fails at 768 pixels with "line that just
    fits: toggle hidden", expected false, received true;
  - at 1215: the build counts the line of 68 characters as 685.8
    pixels, and the test fails at 768 pixels with "one character too
    many: toggle visible", expected true, received false;
  - back at 1233, the test passes at all five column widths, and the
    working tree is clean.

## Cautions

- **The guard is not symmetrical.** The case that fits has a quarter
  of a pixel to spare, so a code font wider than Hack by one unit in
  2048 already stops the build. On the other side, the line of 68
  characters is about ten pixels over the column, so a narrower font
  stops it only when it is about 1.5% narrower: at 1216 over 2048 the
  test still passes. Both agree with the rule of the card: a narrower
  font leaves the page right, a wider one would break it.
- **The guard sees the code font only through the code blocks of the
  code page**, at the column of 768 pixels and over. The table widths,
  which also use Hack's advance for inline code, are guarded by the
  tables' own cases at the limit.
