These are events generated by the hybris platform after each operation
on the database. They are useful to notify some changes and, for
example, to update a search engine (Solr, Elasticsearch, Algolia).

> **Note:** within one transaction, events are not created after each
> operation, but after the transaction is successfully committed.

How the operations on an item within one transaction turn into events:

| Operations on the item | Event generated |
|---|---|
| Created | CREATE |
| Created, then updated twice | CREATE |
| Updated | UPDATE |
| Updated three times | UPDATE |
| Updated twice, then removed | REMOVE |
| Removed | REMOVE |
| Any operation, then the transaction is rolled back | no event |
| Created, updated, then removed | no event |

So we can say: an event is generated only when something actually
different is present in the database.

Be careful: when you change something through a user interface (the
Product Cockpit, for example), the number of items actually changed can
be higher than expected. If you change the category of a product, for
example, an update could be generated for:

- the previous category
- the product
- the final category
- the CategoryProductRelation
- the SaveValueEntry
- the SaveValue

This can be an advantage or a drawback, depending on our needs and our
context, but be careful about the impact on performance of managing
these events.

Anyway, there is an important configuration parameter that lets you
decide whether to manage these events synchronously or asynchronously:

```properties
core.aftersave.async=true
```

You can find it in `advanced.properties`, together with other
configurations:

```properties
# the AfterSaveListeners are notified with the collected AfterSaveEvents asynchronously if true
core.aftersave.async=true

# time interval in ms before the publisher checks again, if the queue for AfterSaveEvents is empty; valid for asynchronous mode only
core.aftersave.interval=200

# number of AfterSaveEvents the AfterSaveListeners deal with at one time; valid for asynchronous mode only
core.aftersave.batchsize=1024

# queue size to store the incoming AfterSaveEvents for the AfterSaveListenerRegistry; valid for asynchronous mode only
core.aftersave.queuesize=1024
```

We will see what the other configurations mean when we discuss how the
event is generated and propagated.

## Definition of AfterSaveEvent

The event is a DTO containing a PK and a type:

```java
public class AfterSaveEvent {
    ...
    private final PK pk;
    private final int type;
    ...
}
```

The type can have the following values:

- `UPDATE = 1`
- `REMOVE = 2`
- `CREATE = 4`

and it describes what kind of change happened on an item. Any other
value of the type raises an
`IllegalArgumentException("wrong operation type")`.

The PK, instead, is the PK of the item changed.

So this DTO is very basic. But how can we intercept it? With an
`AfterSaveListener`.

## AfterSaveListener

It is an interface like this:

```java
package de.hybris.platform.tx;

import java.util.Collection;

public interface AfterSaveListener {
    void afterSave(Collection<AfterSaveEvent> var1);
}
```

To react to an `AfterSaveEvent` you can create your own
`AfterSaveListener`.

Obviously, to keep the impact on the platform's performance low, you
need to:

- reduce the scope of your reaction (you are probably not interested in
  the changes to all items, but only to some types);
- avoid heavy logic in your `AfterSaveListener`.

## Reduce the scope to specific item types

So we have only the PK of an item: how can we filter for specific types
of object without accessing the database?

Actually, in hybris the PK also contains some information about the
type (see
[how to generate hybris PK values without hybris](how-to-generate-hybris-pk-values-without-hybris.html)
for details). We can retrieve what is called the deployment code of the
item with `pk.getTypeCode()`.

The deployment code is related to a specific type, so without accessing
the database we can ignore all the types we are not interested in:

```java
if (!actionableTypeCodes.contains(event.getPk().getTypeCode())) {
    continue;
}
```

where `actionableTypeCodes` can be the set of type codes to consider.

If instead we need more precise information, we can go with:

```java
modelService.getModelType((Object)modelService.get(pk));
```

which fetches the actual type of the object associated with the PK.

Anyway, because normally we need this call only for a very limited
subset of the items of the platform, it is better to make it after the
previous check on the deployment code.

If we want to keep only the list of the types actually managed by the
`AfterSaveListener`, this snippet of code can be useful:

```groovy
String type = 'MyItemType';
String jndiName = Registry.getPersistenceManager().getJNDIName(type);
return Registry.getPersistenceManager().getItemDeployment(jndiName).getTypeCode();
```

It extracts the deployment code from the name of the type we want to
manage.

## Deeper inside

Searching for `AfterSave` in all the Spring XML files, we can find,
among others, `core-spring.xml`, which contains this:

```xml
<!-- AfterSaveEvent listener registry -->
<alias alias="afterSaveListenerRegistry" name="defaultAfterSaveListenerRegistry"/>
<bean id="defaultAfterSaveListenerRegistry" class="de.hybris.platform.tx.DefaultAfterSaveListenerRegistry"
      autowire="byType"/>
```

This class has an interesting method, `publishChanges`.

Putting a breakpoint there and changing an item (the name of a product,
for example), we can check the stack trace to understand the flow
better.

The interesting part related to `publishChanges` is started by a call
in the `Transaction` class, called `notifyCommit`:

```java
public void notifyCommit() {
    try {
        ...
    } finally {
        ...
        // collect changes and publish
        ...
    }
}
```

`notifyCommit()` is called in the final method that frees the
connection after a commit. So every actual change on the database is
notified here.

The method `publishChanges` has two implementations, synchronous or
asynchronous, depending on whether `core.aftersave.async` is true or
false.

The synchronous one is easy: it calls directly all the
`AfterSaveListener`s present, one by one.

### Blocking queue

The asynchronous one, instead, uses a blocking queue in the middle.

The size of this queue is controlled by the `core.aftersave.queuesize`
configuration, which is 1024 by default.

Because it is a blocking queue, it is important to take all the
precautions to keep it from becoming full: otherwise it can block the
publisher thread (:->).

### AfterSaveEventPublisherThread

A thread, `AfterSaveEventPublisherThread`, is created to consume the
queue. It dispatches the stored events to our `AfterSaveListener`.

We can control the execution of this thread with the two remaining
configurations in `advanced.properties`: `core.aftersave.batchsize` and
`core.aftersave.interval`. They are the number of change events the
`AfterSaveEventPublisherThread` fetches at a time, and the interval of
time between one fetch and the next.

Because we are managing a blocking queue here, we have to be careful
that:

1. the `AfterSaveEventPublisherThread` does not die without us knowing:
   it has to be monitored;
2. `core.aftersave.queuesize` is sized correctly, based on the number
   of events that can be generated, balanced against the memory
   available;
3. `core.aftersave.batchsize` and `core.aftersave.interval` are sized
   correctly, based on the amount of CPU we want to use for this
   activity, balanced against the queue size chosen in point 2, so the
   queue does not end up blocked.
